## 1. 문제 정의 (디커플링 워크시트)

### 1-1. 타깃 고객 — "야구에 진심인 3년 차 직장인, 김민수(29세)"

| 구분 | 내용 |
|---|---|
| 기본 정보 | 20대 후반 남성, 서울·수도권 거주, 중소기업 대리, 1인 가구 |
| 디지털 습관 | 스마트폰 헤비 유저, 네이버페이·토스 등 간편결제 상시 이용 |
| 관람 패턴 | 시즌 중 주 1~2회 이상 직관(홈·원정 불문), 티켓팅 앱 3개 이상 사용 |
| 라이프스타일 | 주중 스트레스를 야구 직관으로 해소, 취미·덕질에는 아낌없이 지출 |
| 의사결정 | 친구들과 단톡방에서 즉흥적으로 직관 일정 조율, 티켓 오픈 시간에 민감 |
| 정보 채널 | 야구 커뮤니티, 유튜브 야구 채널, 인스타그램 |

**Pain Point**
- "구단마다 예매처가 달라서 회원가입부터 간편결제 연동까지 따로 해야 하는 게 너무 귀찮고 번거롭다."
- 원정 경기를 갈 때마다 해당 구단의 예매 시스템 UI가 달라 헤맬 때가 많음
- 여러 구단 경기를 예매할 때 통합된 관리나 알림 기능이 없음

### 1-2. 고객 여정과 약한 고리

```
직관 일정 조율 → 티켓 오픈 일정 → [예매 및 결제 진행] → 예매 완료 → 경기 당일
 및 경기 선택      확인 및 대기        ⚠️ 약한 고리         및 티켓 관리   구장 방문·입장
```

**가장 약한 고리:** 예매 및 결제 단계 — 구단별로 다른 예매 시스템을 사용해야 하는 것이 가장 큰 고통

### 1-3. 근본 원인

> **팬은 여러 구단을 오가는데, 예매 시스템은 "구단 단위"로 갇혀 있다.**

1. **계정·결제 정보의 분절** — 회원 정보와 결제수단이 예매처마다 따로 저장돼, 원정·타 구단 경기를 볼 때마다 가입·본인인증·간편결제 연동을 반복
2. **예매 경험의 비표준화** — 좌석 선택 화면, 결제 절차, 선예매 조건·오픈 시간이 구단마다 달라 매번 새로 익혀야 함 → 몇 초가 승부인 오픈 순간에 헤매다 결제 오류·예매 실패
3. **예매 이후 관리의 파편화** — 티켓·일정·동반자 정보가 앱별로 흩어져 "직관 생활 전체"를 한 번에 볼 곳이 없음

⇒ 예매 시스템이 **팬(사람) 중심이 아니라 구단(공급자) 중심**으로 설계된 것이 근본 원인

## 2. 해결 방안

**만루티켓 — KBO 전 구단 통합 예매 플랫폼**

- **디커플링 전략:** 구단별 예매처에 묶여 있던 "예매·결제" 고리를 떼어내, 팬 기준 하나의 고리로 재결합
- **핵심 기능**
  - ⓐ **통합 계정 + 원탭 간편결제** — 한 번 등록하면 전 구단 결제에 그대로 사용
  - ⓑ **전 구단 표준 예매 UI** — 어느 구장이든 같은 좌석 선택·결제 흐름
  - ⓒ **통합 캘린더 + 오픈 알림** — 전 구단 일정·예매 오픈 시각을 한 화면에
  - ⓓ **통합 티켓 지갑 + 동반자 기능** — 모든 모바일 티켓을 한곳에, 친구 몫 일괄 예매·티켓 전달
- **수익 모델:** 홈페이지 광고 + 예매 수수료 + 굿즈·먹거리 사전주문 수수료 + 구단 대상 팬 데이터·마케팅 서비스

> 워크시트 단계에서는 "구단·예매처 독점 계약" 같은 현실 제약은 배제하고, 통합 예매·결제를 직접 제공하는 것을 전제로 설계했습니다.

## 4. 구현 기능

### 메인 페이지
- 흰색 헤더(로고 · 경기 예매 · 구단별 일정 · 좌석 안내 · 고객센터 · 마이페이지 · 내 티켓)
- 야간 야구장 분위기의 네이비 메인 배너 — "오늘의 설렘, 만루티켓"
- 하단 안내 배너와 푸터

### 통합 경기 캘린더
- 월간 달력의 날짜 칸마다 그날 경기를 모두 표시 (끝난 경기는 스코어, 취소 경기는 취소 표시)
- 구단 필터 칩 — 여러 구단 동시 선택 가능
- 경기 표기는 **"원정팀 vs 홈팀"** 순서로 통일 (vs 오른쪽이 홈팀, 구장은 홈팀 홈구장)
- 경기를 누르면 화면 이동 없이 오른쪽 예매 패널에 바로 표시 — 팀·일시·구장·날씨·등급별 가격·예매 버튼, 오픈 알림 토글(화면 표시)
  - 데스크톱에서는 스크롤해도 패널이 화면에 고정, 모바일(768px 미만)에서는 바텀시트로 표시
- 달력 아래 경기 카드 — 선택한 날짜의 경기와 구장 날씨(예시 데이터)
- 관심구단을 정하면 그 팀 경기를 달력에서 강조하고 목록 맨 앞에 표시

### 예매 상태
| 상태 | 조건 | 버튼 |
|---|---|---|
| 예매 예정 | 예매 오픈 시각 전 | 비활성 — "M월 D일 HH:mm 예매 오픈", 오픈 24시간 이내면 "오픈까지 HH:MM:SS" 카운트다운 |
| 예매 중 | 오픈 이후 ~ 경기 시작 전, 잔여석 있음 | [예매하기] |
| 매진 | 예매 중이지만 잔여석 0 | 비활성 — "매진" |
| 예매 종료 | 경기 시작 이후 | 비활성 — "예매 종료" |

- 페이지를 열어 둔 채 오픈 시각이 지나면 새로고침 없이 버튼이 활성화
- 예매 중이 아닌 경기는 예매 화면에 들어갈 수 없고, 결제 직전에도 한 번 더 검사해 거절

### 전 구단 표준 예매 흐름 (4단계)
| 단계 | 내용 |
|---|---|
| 1. 구역 선택 | 부채꼴 구역 배치도(SVG), 구역(등급)별 색 구분, 구역별 잔여석·매진 표시 |
| 2. 좌석 선택 | 직사각형 행-열 그리드, 최대 4석 선택, 행/열 라벨 sticky 고정 |
| 3. 권종 선택 | 일반 / 장애인 / 청소년 인원 입력, **인원 합계 = 선택 좌석 수**일 때만 다음 단계 진행 |
| 4. 결제 | 좌석·권종별 금액·총액 확인 → 등록해 둔 간편결제 수단 선택 → 모의 결제 |

- 같은 구역에 다시 들어올수록 **판매완료 좌석이 늘어나** 실제 예매 경쟁 상황을 재현
- 내가 선택해 둔 좌석은 추가 판매 대상에서 제외

### 회원 · 티켓
- Firebase Authentication **이메일/비밀번호** 로그인 — [가입] / [로그인] 탭, 로그인 후 이메일 앞부분 + [로그아웃] 표시
- 로그인한 사용자만 예매 가능
- 예매 완료 시 Firestore에 티켓 저장 → [내 티켓]에서 구단 상관없이 한곳에 모아보기

### 간편결제 수단
- 네이버페이 · 토스페이 · 카카오페이 · 페이코 중 골라 등록, 기본 결제수단 지정·삭제
- 한 번 등록하면 모든 구단 경기 결제에 그대로 사용 (모의 등록 — 카드번호·계좌번호는 입력받지 않음)

### 티켓 전달 · 정산
- 함께 가는 친구에게 좌석을 전달 — 전달 링크를 열어 수락하면 받은 사람의 [내 티켓]에 표시
- 좌석별 티켓값 정산 요청과 완료 확인 (실제 송금 없음)
- 모의 기능이라 전달·정산 링크는 같은 브라우저에서 열 때만 동작

### 구장 식음료 주문
- 9개 구장 104개 매장의 메뉴를 골라 픽업 시간을 정해 주문 (모의 주문)
- **경기 당일(한국 시간)에만** 주문 가능, 주문 직전에도 재검사
- 주문 접수 → 조리중 → 픽업대기 → 픽업완료 상태 표시

### 좌석 시야
- 구장별 좌석 시야 확인 사이트로 연결 (외부 링크)

### 마이페이지
- 개인정보·비밀번호 변경, 관심구단, 알림 설정, 결제수단 관리
- 예매 내역, **나의 직관 기록**, 식음료 주문 내역, 티켓 전달 내역
- 의견 보내기, 자주 묻는 질문, 약관, 회원 탈퇴(모의 처리)

### 응원 한마디
- 경기별로 응원 글(최대 50자)을 남기고 실시간으로 함께 보기 (Firestore `cheers`)

### 부가 탭
- 경기 기록, 선수 순위(투수·타자 TOP 10, 예시 기록), 현재 순위, 커뮤니티

### 데이터 보안 (Firestore Rules)
| 컬렉션 | 읽기 | 생성 | 수정 | 삭제 |
|---|---|---|---|---|
| `tickets` | 로그인한 본인 티켓만 | 로그인한 사용자, 본인 uid로만 | 불가 | 본인 티켓만 |
| `cheers` | 누구나 (테스트용, 2026-10-31 만료) | 필드 검증을 통과한 글만 | 불가 | 불가 |

- 그 외 경로는 모두 차단

## 6. 실행 및 배포

```bash
# 1. Firebase CLI 로그인 (최초 1회)
firebase login

# 2. 로컬 실행
firebase serve        # 또는 index.html을 브라우저로 열기

# 3. Firestore 보안 규칙 배포
firebase deploy --only firestore:rules

# 4. 호스팅 배포
firebase deploy --only hosting
```

- Firebase 프로젝트 ID: `team03-app-6c22e`
- Firebase 콘솔 설정: Authentication → 로그인 방법 → **이메일/비밀번호 사용 설정**

| 통합 가입·결제와 표준 UI의 편의성 | 한 번의 가입·결제 등록과 동일한 예매 화면이 예매 시간과 실수를 줄일 것 | 10명 대상 **모의 예매 시간 30% 이상 단축**, **도움 없이 완료율 80% 이상** | 두 구단 좌석 선택 → 모의 결제 사용성 테스트 | 구단마다 다른 예매 절차로 혼란을 겪은 간편결제 사용자 |
| 통합 캘린더·오픈 알림의 유용성 | 일정·오픈 시간을 한곳에서 보면 탐색 부담이 줄고 알림을 활용할 것 | 10명 중 **80% 이상 정보 찾기 성공**, **70% 이상 알림 설정 완료** | MVP 체험 링크 제공 후 행동 관찰 및 설문 | 주 1~2회 직관하며 예매 오픈 시간에 민감한 팬 |
| 통합 티켓 지갑·동반자 기능의 필요성 | 티켓을 한곳에 모으고 친구에게 전달할 수 있으면 관리가 편해질 것 | 10명 중 **80% 이상 조회·전달 성공**, **70% 이상 다음 직관에 사용 의향** | 친구와 함께하는 모의 티켓 조회·전달 테스트 후 인터뷰 | 친구 몫까지 함께 예매·전달하는 팬 |

## 8. AI 활용 개발 과정

기획부터 구현까지 AI와 대화하며 반복 개선하는 방식으로 진행했습니다.

### 기획 단계 (Claude)
1. 타깃 페르소나 작성 및 현실성 피드백 (직관 빈도, 지출 규모, 지불 의향 등)
2. 고객 여정 분석 → 약한 고리 정의 → 근본 원인 도출
3. 실제 KBO 구단별 예매처 현황 조사로 문제 정의 근거 보강
4. 디커플링 워크시트(PPT) 3~6번 항목 초안 작성
5. 워크시트 내용 기반 시각 자료 이미지 생성 (GPT)

### 구현 단계 (Claude가 프롬프트 설계 → Claude Code가 구현)
| 회차 | 작업 |
|---|---|
| 1 | 단일 `index.html` MVP — 통합 캘린더, 구단 필터, 상세 패널, 예매 흐름, 내 티켓 |
| 2 | 예매 흐름을 구역 → 좌석 → 권종 → 결제 4단계로 개편, 매수 버튼 제거, 권종 인원 합계 검증 |
| 3 | 좌석 배치를 부채꼴에서 **직사각형 행-열 그리드**로 변경 (라벨 정렬 오류 수정) |
| 4 | 같은 구역 재진입 시 판매완료 좌석이 늘어나는 예매 경쟁 시뮬레이션 |
| 5 | '만루티켓' 브랜드 디자인 적용 (로고, 네이비 테마, 야간 야구장 배너, 반응형) |
| 6 | Firebase 이메일/비밀번호 로그인 + Firestore 티켓 저장 + 보안 규칙 |
| 7 | 구역별 색 구분 복원, "원정팀 vs 홈팀" 표기 통일, 선수 순위 탭 분리 |
| 8 | Firebase CLI로 프로젝트 연결 및 배포 |
| 9 | 경기별 응원 한마디 (Firestore 실시간) |
| 10 | 간편결제 수단 등록, 구장 식음료 주문, 좌석 시야 링크 |
| 11 | 전 구장 식음료 매장, 티켓 전달·정산, 기본 결제수단 오류 수정 |
| 12 | 경기 카드를 달력 아래로 이동, 식음료 주문을 경기 당일로 제한 |
| 13 | 마이페이지 추가, 나의 직관 기록을 마이페이지로 이동 |
| 14 | 달력 날짜 칸에 그날 경기를 모두 표시 |
| 15 | 예매 상태(예정·예매 중·매진·종료) 도입, 오픈 전 예매 차단, 경기 선택 시 자동 스크롤 제거 |

### AI 활용 원칙
- 요구사항을 **변경 사항 / 유지할 기능 / 작업 후 확인**으로 나눠 프롬프트에 명시
- "다른 기능은 건드리지 말 것"을 매번 명시해 회귀 오류 방지
- AI 결과물을 직접 확인하고 문제를 구체적으로 지적해 재요청
  (예: 좌석 도트와 행/열 라벨 불일치, 디자인 적용 후 구역 색 사라짐, 홈/원정 표기 순서)

## 9. 한계 및 향후 계획

### 현재 한계
- 경기 일정·좌석 판매 현황은 **가상 데이터**
- 날씨·선수 기록·경기 결과는 **예시 데이터**
- 결제는 **모의 결제** (실제 PG 연동 없음)
- 간편결제 수단, 티켓 전달·정산, 식음료 주문은 **모의 기능** — 내용이 브라우저에만 저장되어 다른 기기와 공유되지 않음
- 실제 서비스 시 구단·예매처와의 계약, 티켓 오픈 시 대규모 동시 접속 처리(대기열·좌석 선점) 필요
